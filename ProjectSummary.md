# Резюме проекта

## Целевой сегмент

Государственные медицинские организации первичного звена (поликлиники, центральные районные больницы, амбулатории), осуществляющие диспансерное наблюдение пациентов с сахарным диабетом в рамках территориальных программ государственных гарантий и обязательного медицинского страхования.

---

## Проблема

По закону пациенты с диабетом имеют право на бесплатный ежегодный осмотр глазного дна по ОМС для раннего выявления **диабетической ретинопатии** (далее ДР), а медицинские организации обязаны его обеспечить в рамках диспансерного наблюдения.

Однако из-за дефицита врачей-офтальмологов скрининг не проводится в достаточном объеме.

Это приводит к трем последствиям:
1. **Финансовые потери для медучреждения:** штрафы и недоплаты ФОМС за срыв нормативов и позднюю диагностику, снижение стимулирующих выплат по KPI, рост затрат системы на лечение осложнений
2. **Перегрузка врачей-офтальмологов** рутинной работой → дефицит времени на сложные случаи
3. **Недовольство пациентов** → жалобы, проверки, репутационные потери

---

## Предлагаемое решение

**ИИ-система анализа снимков глазного дна**

**Процесс:**
1. Оператор ретинальной камеры делает снимок
2. ИИ обрабатывает снимок: определяет стадию ДР и выделяет проблемные зоны
3. Врач видит размеченный снимок и готовый диагноз → принимает финальное решение

**Результат для медучреждения:**
- Время на анализ одного снимка — секунды вместо минут
- Пропускная способность врача-офтальмолога существенно возрастает
- Нормативы диспансеризации становятся выполнимыми

## Состав прототипа

### Входит

| Компонент                                             | Обоснование                                                                                                        |
|-------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| Бинарная классификация снимков (есть ДР или нет)      | Для задач скрининга достаточно бинарной классификации                                                              |
| Web-приложение (API + простой интерфейс)              | Врачу необходим удобный и понятный способ взаимодействия с моделью, а также возможность зафиксировать свое решение |
| Данные пациентов не храним, максимальная анонимизация | Медицинские данные подпадают под 152-ФЗ; без анонимизации клиника не допустит прототип к тестированию              |

### Не входит

| Компонент                                                        | Причина                                                                                                                                                                      |
|------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Многоклассовая классификация отдельных стадий ДР                 | Компонент не обязателен для скрининга, но открывает перспективу развития продукта в качестве инструмента поддержки клинических решений                                       |
| Сегментация патологических очагов на снимке (микроаневризмы, геморрагии, экссудаты) | Компонент не обязателен для скрининга, но открывает перспективу развития продукта в качестве инструмента поддержки клинических решений                                       |
| Анализ динамики заболевания по снимкам, сделанным в разное время | Компонент не обязателен для скрининга, но открывает перспективу развития продукта в качестве инструмента поддержки клинических решений                                       |
| Возможность просматривать историю инференса                      | Важный компонент будущего продукта, но для прототипа не обязателен. Также есть юридические риски, связанные с хранением медицинских данных                                   |
| Настроенный CI/CD пайплайн + тесты + документация                | Прототип не предназначен для командной разработки и регулярного деплоя. Перечисленное оправдано на production этапе, когда стоит задача масштабировать и поддерживать сервис |
